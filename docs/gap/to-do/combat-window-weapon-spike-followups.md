# Gap: Combat Window Weapon And Spike Followups

Status: Open
Priority: P2

## Need

The Combat Witness rolling windows now expose observed weapon counts, most observed weapon type, and damage spike outliers. That is enough for early backend proof, but more work is needed before the data should drive polished HUD language or operator-facing emphasis.

This gap records the outstanding tasks generated by the weapon/spike metric work.

## Current Implemented Baseline

- Each rolling window has incoming and outgoing `weaponCounts`.
- Each rolling window has `mostObservedWeaponType` for incoming and outgoing damage.
- Each rolling window has `spikeThreshold` and bounded `spikeOutliers`.
- Spike outliers are computed from damage events in the same window and direction.
- Spike outliers carry amount, event time, observed ship label, source label, target label, weapon label, hit quality, and damage type when present.
- Incoming spike `shipLabel` is the observed attacker/source label.
- Outgoing spike `shipLabel` is the observed target label.
- Golden replay now proves the 15 second incoming weapon count and incoming spike outlier path.

## Outstanding Tasks

### P1: Calibrate Spike Detection With Real Datasets

The current spike rule is intentionally lightweight:

```txt
damage spike = damage amount >= average + standard deviation
```

This needs real dataset review before it becomes HUD emphasis.

Tasks:

- Test against longer real combat samples with frigate, cruiser, battleship, drone, missile, turret, and NPC examples.
- Compare `average + standard deviation` against alternatives such as percentile thresholds, median absolute deviation, fixed minimum amount, and window-relative percentage jumps.
- Decide whether tiny windows with 3 events should produce spikes or require a higher minimum sample count.
- Decide whether spike thresholds should be per attacker, per weapon, per direction, or entire direction/window.
- Document the chosen rule in the HUD snapshot schema.

Guardrail:

- Do not label a spike as a threat conclusion. It is only an observed damage outlier.

### P1: Expand Golden Fixtures For Weapon And Spike Cases

The current golden replay proves the basic path, but it does not yet prove enough edge cases.

Tasks:

- Add fixtures with repeated incoming weapon labels so `mostObservedWeaponType` is decided by count, not a single sample.
- Add fixture coverage for tie-breaking when two weapon labels have the same count.
- Add outgoing spike coverage so outgoing `shipLabel` is proven as the observed target label.
- Add fixtures with missing `weaponLabel` to confirm empty weapon labels do not become misleading counts.
- Add fixtures with multiple attackers and multiple weapons in the same 15 second window.
- Add fixtures where a large older hit falls out of the 15 second window and stops appearing as a spike.

Guardrail:

- Keep fixtures exact and fixture-first. Do not infer weapon labels from text that the parser did not explicitly observe.

### P2: Decide Weapon Label Normalization

The current metric counts exact observed `weaponLabel` strings. This is honest but may split the same weapon family across small string variations.

Tasks:

- Decide whether `weaponCounts` should remain exact-label counts forever.
- Evaluate a separate normalized field such as `weaponTypeLabel` or `weaponFamilyLabel`.
- If normalization is added, keep both exact observed label and normalized label.
- Use local/static type metadata only behind a backend boundary.
- Add tests proving that normalization failure does not remove the exact observed label.

Guardrail:

- Do not replace raw observed evidence with a guessed normalized type.

### P2: Clarify Ship Label Semantics

The requested "ship name" is currently represented as an observed log label. In EVE logs that label may be a character, NPC, drone, object, or ambiguous display label, not guaranteed durable ship identity.

Tasks:

- Decide field naming for HUD consumption: keep `shipLabel`, rename to `observedShipLabel`, or expose both with a deprecation plan.
- Document that labels may collide or describe non-ship entities.
- Add fixtures where the source label is a drone/NPC-style label.
- Avoid durable identity claims unless another subsystem later resolves identity with evidence.

Guardrail:

- Do not aggregate permanent threat identity by `shipLabel`.

### P2: Add Renderer Copy Rules Before UI Exposure

These metrics are backend-ready, but UI copy needs guardrails before display.

Tasks:

- Preferred terms: `Observed weapon`, `Most observed weapon`, `Damage spike`, `Observed attacker`, `Observed target`.
- Avoid terms: `primary weapon`, `enemy ship type`, `confirmed ship`, `alpha threat`, `kill risk`, `tank broken`.
- Present spike outliers as recent observations, not warnings by themselves.
- Keep repair balance language separate from spike language.

Guardrail:

- Renderer should consume snapshot fields and not recompute spike logic.

### P3: Performance And Bounds Review

The current windows are bounded and small, but the metric should stay cheap during noisy log bursts.

Tasks:

- Keep per-window spike sorting capped and bounded.
- Confirm behavior with `maxEventsPerWindow` at expected high values.
- Consider keeping only top N spike candidates if future datasets grow.
- Add a stress-style verification if curated datasets become large.

Guardrail:

- Do not add persistent combat history to make spike detection easier.

## Acceptance Signals

- `npm.cmd run verify:combat-replay` covers repeated weapons, ties, missing weapon labels, incoming spikes, outgoing spikes, and pruning.
- `npm.cmd run verify:combat-golden` asserts the selected spike rule.
- Schema docs explain the fields clearly for non-technical review.
- UI copy guidance avoids tactical certainty.
- `npm.cmd run verify:all` passes.
